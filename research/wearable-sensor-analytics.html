00 / the problem

Strength training tells you what moved, not which muscle worked.

Reps, weight lifted, and the coach's eye all measure the outcome of a lift. None of them show how hard an individual muscle is actually working. Surface EMG can — it picks up the electrical activity of a muscle — but raw EMG is noisy, drifts between sessions, and varies from person to person. In its raw form it's useless to a coach.

The task: take raw EMG plus a knee-goniometer signal and turn it into understandable activation information that could support decisions about technique, loading, and recovery. The bar was explicitly not a medical diagnosis — it was a practical, honest analytics foundation the team could build on.

01 / my role

I owned the full pipeline, from messy text files to a validated model.

Inside a team project, this was mine end to end. I was responsible for every stage below and for handing it over in a state another team member could rerun.

  • Data engineering — a robust loader for inconsistent EMG text files, plus quality checks that fail loudly on unusable data.
  • Signal processing — band-pass filtering, rectification, and a linear envelope to get from raw waveform to a readable activation trace.
  • Biomechanical segmentation — using the goniometer to detect and split the recording into individual repetitions.
  • Feature engineering & modelling — sliding-window time-domain features and Random Forest regression across four muscles.
  • Validation & honesty — subject-independent (LOSO) evaluation, and being clear about what the numbers do and don't prove.
  • Handover — saved models, a lightweight serving API draft, documentation, and a clean Git contribution.

I then used the knee-goniometer channel to segment the recording into individual repetitions — smoothing with Savitzky-Golay, detecting movement peaks with adaptive thresholds rather than one fixed cutoff, applying minimum-duration rules (~0.35–0.50 s) and small boundary padding, and visually checking every detection against the movement signal. A fixed threshold works for one athlete and breaks on the next; the goniometer effectively became the label source for the EMG stream.

From each rep I computed activation metrics — mean, peak, iEMG, RMS, variance, waveform length, and time above 40% activation — and for modelling I split the time series into 200 ms windows with a 50 ms hop, turning a high-frequency waveform into a compact table of meaningful features per channel.

03 / decisions that mattered

The judgment calls, and why I made them.

decision_01

95th percentile, not the max, for normalisation

The dataset had no true maximum-voluntary-contraction calibration, so EMG amplitude wasn't comparable between people.

why

Dividing by the single maximum lets one spike distort the whole scale. The 95th percentile gives a robust reference — and I labelled the output as relative activation, never as clinical %MVC.

decision_02

Adaptive rep detection over a fixed threshold

Joint-angle range, baseline, and movement speed all shift between subjects and even between reps.

why

A wrong repetition boundary corrupts every metric computed inside it. Adaptive thresholds read the current signal's own characteristics, so detection held up across recordings.

decision_03

Baselines before the Random Forest

I ran threshold rules, Logistic Regression, KNN, SVM and Gradient Boosting first.

why

Baselines prove the feature table is usable and surface preprocessing bugs early. They also justify complexity — you only earn a heavier model by beating a simple one.

decision_04

LOSO validation, not a random split

Overlapping windows from the same athlete can land in both train and test sets.

why

That leaks subject-specific patterns and inflates the score. Since the real use case is a new athlete, the test had to hold out whole subjects.

A high R² is not proof the system generalises. These numbers hold within the prepared dataset and split. On a new athlete, different hardware, or a live gym, performance would need to be re-earned — which is exactly why I ran subject-independent validation and reported the per-subject spread instead of a single flattering average. Knowing the difference is the point.

05 / challenges

Where it got hard.

challenge_01

Inconsistent source files

Mixed delimiters, variable headers, decimal commas, corrupted rows.

fix

A flexible loader with fallback parsing and explicit quality checks — treated as a reusable component, not a one-off notebook cell.

challenge_02

Explaining it to a coach

Raw waveforms and model stats mean nothing to a non-technical user.

fix

Per-rep summaries, activation bands, and plain-language plots that answer "which muscle worked, and was it consistent?"

challenge_03

Preventing data leakage

Overlapping windows made naive splits look far too good.

fix

Controlled splitting plus LOSO, so the reported score reflects real generalisation, not an easy split.

challenge_04

Large artifacts in Git

Sensor data and model binaries bloat a shared repo.

fix

Git LFS where appropriate and deliberate control over which generated files entered the pull request.

06 / limits & next

What I'd do next.

I shipped a foundation, not a product — and said so. The honest gap list doubles as the roadmap.

  • Collect true MVC calibration so activation can be a real physiological percentage.
  • Validate on new athletes, more exercises, and data collected outside the original dataset.
  • Add confidence / uncertainty estimates to every prediction, and fatigue indicators like median-frequency shift.
  • Harden the serving API — authentication, monitoring, and sub-150 ms inference — and build the full coach dashboard.
  • Add automated tests and drift detection for the pipeline.
